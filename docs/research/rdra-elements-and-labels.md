# RDRA の要素と画面の表示名の調査

sujigaki が持つ RDRA の要素を公開資料と照合し、画面に出す表示名を決める。あわせて、alder の「活動」を RDRA のアクティビティに当てる案を、架空の業務で確かめる。調査日は 2026-11-19。

## 調べた資料

- [RDRA 公式サイト](https://www.rdra.jp/)の手法の説明と、[表形式の RDRA 定義](https://www.rdra.jp/%E8%A1%A8%E5%BD%A2%E5%BC%8F%E3%81%AErdra%E5%AE%9A%E7%BE%A9)
- RDRA 定義・分析シートの各シートの見出し行と「■関連データ」シート（[関連データ形式の調査](rdra-related-data-format.md)を参照）
- [alder の業務設計の構造](https://github.com/mk3008/alder)

RDRA 2.0 の詳しい定義は書籍「RDRA2.0 ハンドブック」にあるが、今回は読んでいない。

## 要素の一覧と表示名

定義・分析シートと関連データに出てくる要素を並べ、画面での表示名を決めた。表示名は、業務部門の人が RDRA を知らなくても読めることを基準にした。説明は公式サイトの記述の要約で、（※）を付けたものは定義・分析シートの構造から読み取った。

| RDRA の要素 | 説明 | 表示名 |
|---|---|---|
| 要求 | 機能要求と非機能要求のシートがある | 要求 |
| アクター | 業務やシステムに関わる人（※） | 登場人物 |
| アクター群 | アクターをまとめたもの（※） | 登場人物のグループ |
| 外部システム | 顧客のシステムなど | 外部システム |
| 外部システム群 | 外部システムをまとめたもの（※） | 外部システムのグループ |
| 業務 | 業務 | 業務 |
| BUC（ビジネスユースケース） | 業務フローの単位 | 業務フロー |
| アクティビティ | BUC で価値を届けるステップ | 活動 |
| UC（ユースケース） | 「XX を YY する」の形で書く | システム操作 |
| 画面 | UC と人の操作の関係として出てくる | 画面 |
| イベント | UC と外部連携の関係として出てくる | イベント |
| タイマー | 定期的に動くきっかけ（※） | 定期処理 |
| コンテキスト | 情報・状態モデル・条件・バリエーションをまとめるもの（※） | 分類 |
| 情報 | システムが保持するもの | 情報 |
| 属性 | 情報の項目（※） | 項目 |
| 状態モデル | 状態をまとめたもの（※） | 状態の流れ |
| 状態 | 情報の変化 | 状態 |
| 条件 | ビジネスルール | 業務ルール |
| バリエーション | 条件の軸になるもの | 区分 |
| 値 | バリエーションの値（※） | 区分の値 |

「説明」と「Stereotype」は、関連データでは要素として扱われているが、sujigaki では要素の属性として持つ。利用シーンと帳票は、定義・分析シートにも関連データにも出てこないため、今回は対象にしない。

## 要求のつながり

定義・分析シートの「機能要求」シートの列は、分類・アクター・機能要求・説明である。要求はアクターとつながり、業務や BUC とはつながらない。関連データには、要求の行がない。

sujigaki は「要求 → 業務 → システム操作 → 画面・情報」のつながりをたどれることを目的にしている。そのため、要求と業務のつながりは、sujigaki 独自の関係として持つ。要求とアクターのつながりは、RDRA と同じく持つ。

## 「活動」の対応

alder の Activity は「担当者がひと続きに進める仕事」で、担当者や判断する人が変わる所と、待ちが発生する所で分ける。RDRA のアクティビティは「BUC で価値を届けるステップ」で、アクターと関係づけられる。どちらも業務フローの中の1ステップを指すので、alder の Activity は RDRA のアクティビティに当てる。

### 架空の業務で確かめる

架空の会社の「研修の受講申込」の業務フローで確かめた。

| 順 | 活動 | 担当 | 区分 | システム操作 | 画面 | 情報 |
|---|---|---|---|---|---|---|
| 1 | 受けたい研修を選んで申し込む | 受講者 | システム利用 | 研修に申し込む | 研修一覧、申込入力 | 研修、申込 |
| 2 | 申込を承認する | 上長 | システム利用 | 申込を承認する | 承認待ち一覧 | 申込 |
| 3 | 定員を確かめて受講を確定する | 研修担当 | システム利用 | 受講を確定する | 申込一覧 | 申込、研修 |
| 4 | 受講案内をメールで送る | 研修担当 | 手作業 | なし | なし | なし |

- 1から2、2から3は、担当者が変わり、承認を待つ時間もある。alder の分け方でも、RDRA のアクティビティとしても、別の活動になる。
- 3と4は、担当者が同じで、待ちもない。alder の分け方だけなら1つの活動にまとめられる。しかし、3はシステムを使い、4は使わない。sujigaki は活動ごとに区分（手作業／システム利用）を持つので、まとめると区分を1つに決められない。

この結果から、活動を分ける所に「区分が変わる所」を加える。

## 要件定義書への反映

- 4.1 節の表示名を、上の表に置き換える。本文の呼び名もそろえる。
- 要求と業務のつながりを、sujigaki 独自の関係として前提条件に書く。
- FR-002 に、活動を分ける目安（担当者や判断する人が変わる所、待ちが発生する所、区分が変わる所）を書く。
