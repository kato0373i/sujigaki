## 1. 方針

テストで守るのは、次の4つである。

1. **モデルの規則が正しい**: つながりの規則、確認状態の遷移、権限、検証の結果（FR-001、FR-013、FR-040、FR-081）
2. **変更が失われない**: 同時に編集しても、衝突を見逃して上書きしない（FR-070、NFR-005）
3. **権限の外の操作を通さない**: 画面を経由せずに API を呼んでも拒否する（NFR-006）
4. **書き出したものを読み戻せる**: YAML に書き出して読み込むと、元のモデルに戻る（FR-050、NFR-015）

規則はできるだけ `packages/domain` と `packages/interchange` に寄せ、I/O のない UT で確かめる。UT で確かめられないもの（データベース、ファイル、HTTP、認証、ブラウザ）だけを、IT と E2E で確かめる。上の層ほど遅く壊れやすいため、件数を絞る。

## 2. テストの層

| 層 | 対象 | 外部との接続 | 道具 | 実行するとき |
|---|---|---|---|---|
| UT | `packages/domain`、`packages/interchange`、`apps/server` のアプリケーション層、`apps/web` の表示の計算 | なし。保存先はメモリ上の実装に差し替える | Vitest、fast-check | すべての PR とコミット |
| IT | `apps/server` の API・保存先・マイグレーション・ローカルモードのファイル | PostgreSQL と一時フォルダーに実際につなぐ。ID プロバイダーは使わない | Vitest、Hono の `app.request()` | すべての PR |
| E2E | 利用者の主な操作の流れ | 画面・API・PostgreSQL・Keycloak をすべて起動する | Playwright、axe-core | `apps/web` か `apps/server` を変える PR と、main への反映 |

件数の目安は UT が大半で、IT は API と保存先の境界ごとに数件、E2E は5本程度とする。

## 3. UT

### 3.1 対象と書き方

- ドメインの集約は `Result` の成功と失敗の両方を確かめる。失敗はエラーコードだけでなく、画面に出すメッセージも確かめる。
- モックのライブラリは使わない。日時は引数で渡し、ID は呼び出し側で作るため、差し替えが要らない。
- アプリケーション層はリポジトリをメモリ上の実装に差し替えて確かめる。メモリ上の実装と PostgreSQL の実装は、同じ IT を通す（4.1 節）。
- テストの要素や問いは、`packages/domain/src/testing` の作成関数で作る。各テストには確かめたい項目だけを書く。

### 3.2 性質のテスト

入力の組み合わせが多い規則は、個別の例に加えて、fast-check でどの入力でも成り立つ性質を確かめる。

| 対象 | 性質 |
|---|---|
| つながりの規則 | 2つの種類をどちらの順で渡しても、同じつながりの種類になる。つなげない組は、どちらの順でも拒否する |
| 確認状態の遷移 | どの状態とロールの組でも、`availableReviewStates` が返す状態にだけ遷移できる |
| 要素の編集 | 内容を変える編集をすると、どの確認状態からも未レビューに戻る。内容が同じ編集では、バージョンも確認状態も変わらない |
| 権限の表 | ロールを強くすると、できる操作は減らない |
| メンバー構成 | どの順に操作しても、管理者が0人にならない |
| YAML の読み書き | 書き出して読み込むと、元のモデルと同じになる。書き出し直しても同じ YAML になる |
| 取り込みの差分 | 差分を元のモデルに当てると、取り込んだモデルと同じになる。当てたあとにもう一度差分を出すと、変更はない |

性質のテストが失敗したときは、fast-check が示す最小の入力を、個別の例のテストとして残す。

### 3.3 カバレッジ

`packages/domain` と `packages/interchange` は行のカバレッジ95%以上、分岐のカバレッジ90%以上を CI の合格の条件にする。数値は抜けを見つけるための目安であり、数値を上げるためだけのテストは書かない。`apps/` のカバレッジは測るだけにして、合格の条件にはしない。

## 4. IT

### 4.1 保存先

- PostgreSQL は、CI ではサービスコンテナー、手元では `docker compose` で起動する。テストの初めにマイグレーションを空のデータベースに当て、マイグレーションそのものも確かめる。
- テストごとにトランザクションを始め、最後に取り消す。並列で動かすときは、ワーカーごとにデータベースを分ける。
- リポジトリの IT は PostgreSQL の実装とメモリ上の実装の両方に同じテストを通す。メモリ上の実装が本物とずれないようにするためである。
- ローカルモードのファイルの実装は一時フォルダーに YAML を書き、読み戻して確かめる。分け方（ADR-006）どおりのファイルができることも確かめる。

### 4.2 API

- Hono の `app.request()` で、HTTP サーバーを立てずにリクエストを送る。ログインはテスト用のセッションを直接作って済ませ、ID プロバイダーは使わない。
- 権限は `PERMISSIONS` の表とエンドポイントの対応から、ロールとエンドポイントのすべての組を生成して確かめる。必要なロールより弱いロールでは `FORBIDDEN` が返り、データが変わらないことを確かめる（NFR-006）。
- エラーは設計書 5.2 節のコードと `application/problem+json` の形で返ることを確かめる。
- 同時編集は同じ要素に10件の更新を並列で送り、1件だけが成功して残りが `VERSION_CONFLICT` になることを確かめる（NFR-005）。変更の一式（`change-sets`）では、1件でもバージョンが合わなければ何も反映されないことも確かめる。

## 5. E2E

利用者の操作の流れのうち、画面と API とデータベースをまたいで初めて確かめられるものだけを書く。

| # | 流れ | 主な要件 |
|---|---|---|
| 1 | Keycloak でログインし、要素を作ってつなぎ、業務フローに表示される | FR-010、FR-020、FR-080 |
| 2 | 業務責任者が確認済みにし、編集者が内容を変えると未レビューに戻る | FR-013、FR-030 |
| 3 | 2つのブラウザで同じ要素を編集し、後の保存で衝突のダイアログが出る | FR-070 |
| 4 | YAML を読み込み、差分から一部の変更だけを採用する | FR-050、FR-052 |
| 5 | ローカルモードでフォルダーを開いて編集し、YAML のファイルが書き換わる | FR-061 |

- 画面の要素は役割と表示名（`getByRole` など）で探す。CSS のクラス名には頼らない。
- 各画面で axe-core の検査を通す。色だけで区別していないか（NFR-017）は、区分と確認状態の表示を個別に確かめる。
- CI では失敗したテストを1回だけやり直す。やり直して通ったテストは不安定なテストとして Issue に起票し、放置しない。

## 6. 要件との対応

- 要件定義書の受け入れ条件は確かめられる一番下の層でテストにする。たとえば FR-082 の「最後の管理者を外す」は、メンバー構成の UT で確かめる。
- 受け入れ条件を確かめるテストは、`describe` の名前に要件の ID を入れる（例: `FR-082 メンバーを管理する`）。要件の ID で検索すれば、対応するテストが見つかる。
- 非機能要件は次のように扱う。

| 要件 | 確かめ方 |
|---|---|
| NFR-001、NFR-002 | プロトタイプの後に、1万件の要素で読み込みと描画の時間を測る。目標値が決まるまでは、合格の条件にしない（[Issue #7](https://github.com/kato0373i/sujigaki/issues/7)） |
| NFR-005 | 4.2 節の同時編集の IT |
| NFR-006 | 4.2 節の権限の IT |
| NFR-007 | CI で秘密情報の検査を通す |
| NFR-015 | 古いバージョンの YAML をテストのデータとして残し、読み込めることを UT で確かめる |
| NFR-016 | 利用者テストで確かめる。自動のテストでは扱わない |
| NFR-017 | 5章の axe-core の検査と、表示の個別の確認 |

## 7. 対象外

- 画面の見た目の差分（ビジュアルリグレッション）は、画面が固まるまで扱わない。
- ミューテーションテストは CI に入れない。ドメインの規則を大きく変えたときに、手元で Stryker を動かしてテストの抜けを探す。
- AWS の環境そのもの（CDK の出力）は、スナップショットのテストにとどめる。
